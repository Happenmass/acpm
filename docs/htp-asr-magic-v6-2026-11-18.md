# Magic V6 上 24 秒 ASR 与 OnSpeak47 的速度差距

2026-11-18。荣耀 Magic V6，SM8850、Hexagon V81、Android 17、4 KiB 页。OnSpeak47 v2.2.0-npu 使用 87,193 词表、512 槽 KV 及中英越微调权重。SDK 使用官方 Qwen3-ASR-0.6B 检查点、151,936 词表、1,024 槽共享 KV 和已去掉 KV head 复制的 GQA 图。第一轮调优保留了 SDK 的模型文件。后续完整图实验沿用同一权重和 24 秒上下文，重新编译两张解码图。

## 同一段公开 PCM

公开 24 秒音频的 SHA-256 为 `a2736f5cf5760dab9de3966856f7851af52c3ede2dbe9bcf112a846fdab5638f`。OnSpeak47 从同一 worker 顺次识别三个无损 8 秒切片。两个 SDK 配置各一次识别全段。每组单独加载模型，关闭 profiling，轮换执行顺序三轮，主机用同一单调时钟计至收到结果。设备热状态为 1，首个旧版样本从 2 降至 1。表中为各指标中位数。

| 配置 | 模型就绪后识别 | 含进程与模型加载 | AR1 调用数 |
|---|---:|---:|---:|
| OnSpeak47 8 秒 × 3 | 2.069 s | 4.517 s | 83（此前同音频 trace） |
| SDK 24 秒，原 TURBO | 4.378 s | 5.945 s | 75 |
| SDK 24 秒，高性能档与优化后的 Mel | 3.205 s | 4.724 s | 75 |

高性能档少用 1.173 s（26.8%），剩余差距 1.136 s。各轮的 75 个 token ID 均逐一匹配原 24 秒参考。表中高性能配置固定核心与总线为 MAX，以便归因。最终 SDK 逐窗按 Android 热状态选档，持续负载另测。

## 哪些改动带来收益

- 保持模型、前处理和二进制相同，只把 QNN DCVS 的核心和总线从 TURBO 请求到芯片支持的 MAX。四轮交错，每次模型加载后连跑两次。AR1 中位数从 48.33 到 35.98 ms/token，全窗从 4.355 到 3.261 s。在独立拆项对照中，单升总线约 46 ms/token，单升核心约 39 ms/token，两者都升约 36–38 ms/token。未读取实际时钟频率。
- 单独固定 MAX，对比 Mel 前端。FFT 直接在输出缓冲区合并两半，每个 Mel 滤波器只累加首尾非零频点之间的区间。24 秒 Mel 阶段中位数从 165 到 71 ms。36 组主机差分用例覆盖静音、脉冲、固定种子噪声、补齐和窗长边界，每个输出 float 的位模式都一致。
- MAX 之外另测 RPC polling、DDR 性能模式与 HMX 单独投票，组合结果约 35–36 ms/token。两次顺序相反的测试中，整段收益小且受前处理抖动影响。SDK 采用核心与总线修改。
- 24 秒模型在本轮各组比较中均复用跨图 KV。换用 QAIRT 2.51 执行同一新版 AR1，仅改变运行库，固定输入下用时与 2.50 接近。结果见下表。

## 历史 K 布局实验

在真机通过 QNN API 创建一层 FP16 GQA 子图，8 个 KV head、每组两行 query、128 维 head、1,024 个历史槽，360 个可见位置。Q 已预先缩放，四张图共用相同输入数值、mask、softmax 和 PV。每图 5 次预热及 50 次计时，交换顺序共三轮。各图与 FP32 参考转 FP16 的最大绝对误差均为 0.000489 以内。

| QK 做法 | 单层图调用，三轮中位数的中位数 |
|---|---:|
| 常规布局，拼接新 K 后计算 QK | 0.342 ms |
| 历史 K 预转置，拼接新 K 后计算 QK | 0.234 ms |
| 常规布局，分别计算历史和当前分数再拼接 | 0.274 ms |
| 历史 K 预转置，分别计算两部分分数 | 0.222 ms |

单层实测支持继续尝试预转置 K。整模型需要同时修改 AR64 和 AR1 的共享 K 输入布局、prefill 写入及逐 token 回写。子图测量不含这些成本，也未覆盖完整模型的编译调度。完整图结果见下文。

## 持续运行、冷启动与应用内验收

固定同一档位时，每组连续处理 8 个满窗，按 TURBO、MAX、MAX、TURBO 的顺序测量。两组 MAX 的单窗中位数为 3.29 和 3.31 s，第二组结束时热状态已从中度升至严重（Android 等级 3）。这一试验没有采集功耗或能量。

SDK 最终实现仅在窗口开始时为 Android 热状态 NONE 或 LIGHT 请求 MAX，达到 MODERATE 或读数不可用时请求原 TURBO，窗口结束释放投票。服务在取得 worker 请求锁后读取 PowerManager，把本窗档位随内部请求发给 worker。只有标记 burst 的请求才使用 MAX，原有只提供 WAV 路径的请求继续使用 TURBO。

先用在原生侧读取热状态的验证版本，单进程连续识别 24 个满窗，共 9 分 36 秒音频。前 16 窗开始时为 LIGHT，中位数 3.310 s、36.67 ms/token；后 8 窗开始时为 MODERATE，中位数 4.400 s、49.36 ms/token。1,800 个输出 token 逐一匹配。整轮 worker 的峰值 RSS 为 750,460 KiB（733 MiB）；独立固定档探针约 712 MiB。随后的 SDK APK 将读热状态移至已有服务进程，避免 worker 为该查询额外链接 libandroid。下列 App UID 对照使用最终实现。

另用 8.802 秒中英合成 WAV，在固定 MAX 的独立探针上，以三个新进程各跑首窗和紧接的复用窗。basic profile 的 186 次 AR1 都有逐步记录，首步 35.80–36.87 ms，任一步最高 37.23 ms。此前 App 偶发多秒的冷 Decode 长尾在该样本中没有复现，尚无证据解释其成因。

录音豆隔离测试包从实际 Binder 客户端连续发起 24 次同一公开 WAV 的识别。WAV 还原后的 float PCM 与上表输入 SHA-256 相同。每次返回的全文都与原版参考的 SHA-256 一致，后 23 窗均命中已加载模型。扣除第一个含加载窗口后，14 个从 LIGHT 开始的窗口调用耗时中位数为 3.301 s，9 个从 MODERATE 开始的窗口为 4.379 s。每窗计时含客户端到服务的往返。重复相同音频用于核验持续吞吐及窗间切档，未覆盖自然会议多样性。

SDK 自己的 App UID 在 8.802 秒中英合成 WAV 上跑三组模型冷/热请求，校验两次空闲卸载再加载、每次 31 token 和全文相等。在起止热状态均为 LIGHT 的一组中，热请求中位数 1.384 s，六次中的 worker 峰值 RSS 为 735,216 KiB（718 MiB）。供对照，原生 worker 查热状态的试验包同样三组峰值为 780,616 KiB（762 MiB）。跨应用测试还核验了服务 PID、第二次加载时间为零、两次全文相同及说话人服务响应。补上热状态 API 异常处理后的构建再跑三冷三热，起止热状态均为 MODERATE，热请求中位数 1.862 s，六次全文一致，跨应用测试再次通过。

## 复核 MLP 与词表头，改用 AR1 O3 编译

2026-11-18。上一轮估算采用「该阶段节点周期之和 ÷ 全图节点周期 × 全图 HTP 活跃时间」。在归档的三轮 detailed profile 中，普通 K → 预转置 K 的全图周期中位数从 199.14M 降到 155.98M，整图活跃时间仅从 33.85 降到 32.80 ms。同期 28 层 MLP 原始计数为 56.15M → 55.48M，词表头为 35.83M → 35.37M。两组分到的整图时间比例随分母缩小而增大。另起三轮固定输入真机复测，MLP 为 55.95M → 55.53M，词表头为 35.54M → 35.22M。现有观测不支持将先前的分摊值解读成这两个阶段的实际耗时回退。

### AR8 处理最后一个预填充块

从原 AR64 导出同权重的 AR8，调整序列和 GQA 的 reshape、mask，保留 RoPE 的特征维度。三图共享历史 KV。标准满窗前五次预填充各含 64 个有效位置，最后一次只有 7 个。用 AR8 处理尾块后，六轮完整预填充中位数从 311.8 降至 294.6 ms，每轮节约 14.5–19.4 ms。整段从 2.076 到 2.026 s，六轮中有四轮变快，AR1 耗时也在波动。满窗 75 个 token 全部一致，候选的峰值 RSS 中位数多 5,152 KiB。

### 后续优化优先级

1. 优先将短/长历史 AR1 路由作为 SDK 候选验证。已有同场 12.8% 整段收益和跨边界 token 对照。发布前还需真实 SDK/Binder 下的冷启动、长期热复用、多语言逐 token 和持续负载回归。可以在相同路由设计里单独测试 384 槽，衡量再加一张图的加载与内存成本。
2. 为中间预填充块导出只产生 KV 增量的图。当前 worker 在前五块计算的 `next_id` 都会被下一块覆盖，只有尾块预测的 token 会被消费。保持最后一块沿用原 AR64，测省去五次词表投影与选词的整段收益；编译器也可能裁去最后一层在生成 K/V 后的计算。此项尚无真机时间数据。
